# 实验设计：Containment Audit

## 实验目标

判断：

> 实验6能够恢复的样本，其关键答案信息是否已经存在于UA3实际获得的memory集合中。

注意：

不是比较gold evidence。

而是比较：

```
raw retrieved memories
        ↓
是否包含回答所需事实
        ↓
如果包含，为什么UA3没利用
```

* * *

# Step 1：准备数据

取：

```
UA3错误 + 实验6正确
= 158条
```

每条保存：

### 1\. 问题

例如：

```
Who supported Donna during her health challenges?
```

### 2\. gold evidence

实验6使用的：

```
Donna's sister provided significant support...
```

### 3\. UA3实际输入的retrieved memories

注意这里必须是：

```
memos返回结果
```

不是HaluMem原始gold。

例如：

```
Memory 1:
Donna received support from family.

Memory 2:
Donna had health challenges.
```

* * *

# Step 2：设计审计标签

人工或者LLM辅助判断：

## Label A：Evidence Missing

定义：

> 答案需要的关键事实，在memos返回memory中不存在。

例：

问题：

```
Who supported Donna?
```

gold：

```
Donna's sister supported her.
```

retrieved：

```
Donna received support from family.
```

缺：

```
sister
```

所以：

```
A = missing
```

责任：

```
memory writing / compression
```

不是你的方法。

* * *

## Label B：Evidence Present but Not Rendered

定义：

> 返回对象里存在，但你的统一解析没有展示出来。

例如：

原始memory：

```json
{
memory_text:
"Donna received support",
metadata:
{
 supporter:"sister"
}
}
```

你的UA3：

```
Donna received support
```

丢了：

```
supporter=sister
```

标签：

```
B
```

责任：

```
unified adapter
```

这是你最应该优化的地方。

* * *

## Label C：Evidence Rendered but Not Used

定义：

模型已经看到正确证据。

例如：

context：

```
[M1]
Donna's sister supported her.
```

但是回答：

```
Donna's friend supported her.
```

标签：

```
C
```

责任：

```
decision/rendering/prompt
```

* * *

## Label D：Judge Error

比如：

实验6认为答对，但实际上回答不完整。

标签：

```
D
```

# Step 4：统计结果

你真正需要的是这个：

假设结果：

| 类型 | 数量 | 比例 |
| --- | --- | --- |
| Missing | 90 | 57% |
| Not Rendered | 45 | 28% |
| Not Used | 18 | 11% |
| Judge Error | 5 | 3% |

那么你的论文故事会变成：

> 直接gold evidence能够恢复158条错误，但其中57%来自memory content loss，并非post-retrieval admission failure。冻结检索条件下，真正可由准入层改善的是63条。

这非常重要。

因为它证明：

你的方法不是没做到72.7%，而是：

```
系统瓶颈：

memory writing loss
        ↓
retrieval loss
        ↓
admission loss
        ↓
generation failure
```

你是在解决第三层。

# 为什么不是先改统一解析？

因为现在你还不知道统一解析能救多少。

假设：

158里面：

-   missing 130条
-   render loss 28条

那么你花一周改renderer，理论收益最多28条。

这就是研究中很容易踩的坑：

> 看到一个错误现象，就直接优化最靠近自己的模块。

但系统错误传播是流水线：

```
write
 ↓
retrieve
 ↓
parse
 ↓
admission
 ↓
render
 ↓
generate
```

前面的损耗会吞掉后面的优化空间。
